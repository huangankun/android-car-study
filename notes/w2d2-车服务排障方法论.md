# 车服务排障方法论 + 场景手册

> 配套：`w2d2-dumpsys-car-service实验-stepper.md`（命令细节）
> 目的：把 W2D2 的命令从「背下来」变成「用得出来」。核心不是命令表，是**判断链路断在哪一段**的方法。

---

## 一、先讲方法：为什么不能"上来就敲命令"

新手排障的通病：现象一出现，脑子里一片命令，挨个试。
高手排障：**先问「这个现象，最可能断在哪一段」，然后用一条命令把链路切成两半，砍掉一半可能性。**

车控属性问题的链路是固定的：

```
┌────────┐   ┌──────────────┐   ┌─────────────────┐   ┌──────────────────┐   ┌─────┐
│ CAN/   │──▶│ Vehicle HAL  │──▶│ CarProperty     │──▶│ CarProperty      │──▶│ App │
│ 信号   │   │ (IVehicle)   │   │ Service         │   │ Manager (App侧)  │   │ UI  │
└────────┘   └──────────────┘   └─────────────────┘   └──────────────────┘   └─────┘
   ①车端         ②HAL 层            ③服务层               ④客户端 API          ⑤界面
```

**核心方法：沿链路二分。**
现象出现时，先用命令验证**链路的某一段**：
- 值在 ③ 层对不对？→ 一条 `get-property-value` 就能判断
- 值对、UI 不动 → 断在 ④⑤（订阅/回调/UI）
- 值就不对 → 断在 ①②（HAL/CAN）

**一次命令砍掉一半链路，比挨个试快十倍。**

## 二、分层定位框架（排障的"地图"）

按从下到上排，**先低层后高层**（低层不通，高层怎么查都白搭）：

| 层 | 问题 | 用哪条命令 | 判据 |
|---|---|---|---|
| **L0 系统** | CarService 起来了吗？ | `adb shell service list \| grep car_service` | 有 `car_service: [android.car.ICar]` |
| **L1 服务** | 这个 CarXxxService 活着吗？ | `dumpsys car_service --list` + `--services X` | 名字在列表里、dump 有内容 |
| **L2 属性存不存在** | 这个属性 VHAL 支持吗？ | `cmd car_service get-carpropertyconfig <id>` | 有 `Property:0x...` 记录 |
| **L3 值对不对** | 当前值是什么？ | `cmd car_service get-property-value <id>` | 读到的值 vs 预期值 |
| **L4 能不能写** | 写失败是谁拒的？ | `cmd car_service set-property-value ...` | 成功 / `code 4 = ACCESS_DENIED` |
| **L5 事件推不推** | 变化能到订阅者吗？ | `inject-vhal-event` + 订阅者 | 订阅者收到事件 |
| **L6 裸接口** | 底层 binder 通不通？ | `service call car_service <code>` | 返回 Parcel / 异常 |

> 记忆口诀：**"系统活、服务在、属性有、值对、能写、能推、能通"** —— 七层从下往上过一遍。

## 三、场景手册（把命令放回真实问题里）

### 场景 1：空调温度显示不刷新（最常见的"UI 不动"）

**现象**：调了空调温度，屏幕上的数字没变。
**怎么想**：先别怀疑 UI。问"值本身变了吗"。
**命令**：
```bash
adb shell cmd car_service get-property-value 0x1140050e   # 空调温度显示单位
adb shell cmd car_service get-property-value 0x15200505   # HVAC_AC_ON（看 zone 和值）
```
**判据**：
- 值**变了**，UI 不动 → 断在 ④⑤：CarPropertyManager 订阅没注册 / 回调没触发 / UI 没刷新
- 值**没变** → 断在 ①②：VHAL 没收到 CAN 信号，或信号映射错
**结论**：一条命令就把"UI 问题"和"信号问题"分开了。

---

### 场景 2：仪表车速不动（连续型属性的坑）

**现象**：车在动，仪表车速一直是 0。
**怎么想**：车速是 `changeMode:0x2`（CONTINUOUS）属性，靠采样推送。
**命令**：
```bash
adb shell cmd car_service get-carpropertyconfig 0x11600207   # 先看配置
adb shell cmd car_service get-property-value 0x11600207      # 再看当前值
```
**判据**：
- 配置里 `changeMode:0x2`、`fs min:1.0 fs max:10.0` → 这是按 1~10Hz 采样的属性
- `get-property-value` 读到 `0.0` → 值就没上来，断在 ①②
- 读到 `22.5` 但仪表是 0 → 断在 ④⑤（订阅/UI）
**面试点**：能说出"连续属性 vs 变化上报属性（ON_CHANGE）"的区别，就赢一半。

---

### 场景 3：某个车功能"整个没反应"（服务没启动）

**现象**：投屏功能点了没反应，怀疑服务没起来。
**怎么想**：先看服务在不在，再看特性开没开。
**命令**：
```bash
adb shell dumpsys car_service --list | grep -i projection
adb shell dumpsys car_service --services CarProjectionService
adb shell dumpsys car_service --services CarFeatureController   # 看 mEnabledFeatures
```
**判据**：
- `--list` 里没有 → 服务没注册
- `mEnabledFeatures` 里没有 `projection` → 特性被关（可能是 OEM 配置/镜像裁剪）
**结论**：这比"看日志猜"快得多——一条 `--list` 就知道服务在不在。

---

### 场景 4：写属性报错（分清"谁拒的"）

**现象**：调 `set-property-value` 报错，不知道是权限还是只读。
**命令**：
```bash
adb shell cmd car_service get-carpropertyconfig 0x11400400   # 看 access
adb shell cmd car_service set-property-value 0x11400400 0 8  # 试写
```
**判据**：
- `access:0x1` + 报 `(code 4)` → **只读属性，VHAL 拒的**（ACCESS_DENIED）。档位这种"车自己产生"的信号，App 本来就不该写
- `access:0x3` 却还报错 → 再看是不是权限（`SecurityException`）
**结论**：错误信息里看类名——`VehiclePropValue` 开头的是 **VHAL 拒的**，`SecurityException` 是**权限层拒的**。分清了才知道找谁。

---

### 场景 5：注入事件后 UI 没反应（理解"事件 ≠ 状态"）

**现象**：用 `inject-vhal-event` 注入了车速 22.5，仪表还是 0。
**怎么想**：注入到底改了什么？
**命令**：
```bash
adb shell cmd car_service inject-vhal-event 0x11600207 0 22.5
adb shell cmd car_service get-property-value 0x11600207   # 还是 0.0
```
**判据**：`get()` 读的是**真实存储值**，注入只伪造"上报事件"给**订阅者**。没有订阅者，事件就丢了。
**结论**：这是设计（`injectVhalEvent` 源码只有 `onPropertyEvent` 一行）。**要看到注入效果，得写一个订阅者**；`get` 永远看不到。
**记忆点**：`inject` = "车说它变了"；`set` = "我让它变"；`get` = "它现在是多少"。

---

### 场景 6：`service call` 报 SecurityException（权限层）

**现象**：`service call car_service 16` 返回一大串 `requires android.car.permission...`。
**判据**：shell UID 没有该权限。`service call` 是裸 binder，不走 CarService 的权限包装。
**结论**：要么换不需要权限的方法，要么 `adb root`。**这也是为什么工程上少用 `service call`**——它绕过了权限和解析，只适合"验证 binder 通不通"。

---

### 场景 7：夜间模式不切换

**现象**：进隧道了，屏幕不切夜间模式。
**命令**：
```bash
adb shell cmd car_service get-property-value 0x11200407   # NIGHT_MODE 当前值
adb shell cmd car_service day-night-mode night            # 强制切一下试试
```
**判据**：
- 手动切有效 → 自动逻辑（光照传感器/CAN）没触发，查 `CarNightService` 的 policy
- 手动切无效 → 显示/主题层问题

---

### 场景 8：休眠/唤醒异常（电源层）

**现象**：锁车后系统不休眠，或唤醒慢。
**命令**：
```bash
adb shell dumpsys car_service --services PowerManagementService
```
**判据**：看 `mCurrentState`、`mCurrentPowerPolicyId`、`mShutdownOnNextSuspend`、组件开关（`Power components state`）。

| 我要… | 命令 | 注意 |

| 裸 binder 验证 | `service call car_service <code>` | 码 11~19；返回原始 Parcel |

## 五、面试怎么讲（30 秒模板）

> 问："你怎么排查一个车控属性读不到/不刷新？"

**模板（分层二分 + 具体命令）**：
1. **先定层**：车控属性链路是 `VHAL → CarPropertyService → CarPropertyManager → App`。
2. **先读值**：`cmd car_service get-property-value <id>` 看 VHAL 真实值对不对——这一步就把链路砍成两半。
3. **值不对** → 查 `get-carpropertyconfig` 看属性存不存在、`changeMode`（连续/变化上报）、`access`；再查 HAL/信号。
4. **值对但 UI 不动** → 查 `CarPropertyService` 的 client/订阅、`CarPropertyManager` 回调、UI 层。
5. **写失败** → 看错误码：`code 4 = ACCESS_DENIED`（只读，VHAL 拒）vs `SecurityException`（权限）。
6. **要模拟车端信号** → 用 `inject-vhal-event` + 订阅者，别指望 `get` 能看到。

**追问加分项**：
- 能说清 `access:0x1/0x3`、`changeMode:0x1/0x2` 的语义
- 能说清 `inject` 是事件、`set` 是状态、`get` 是真实值
- 能说清"错误信息里的类名告诉你谁拒的"

## 六、怎么练（自己造场景）

1. 打开 AAOS 模拟器，随便挑 3 个属性（`grep -iE "HVAC|GEAR|SPEED"`）。
2. 对每个属性走一遍七层：`--list` → `get-carpropertyconfig` → `get-property-value` → `set`（看能不能写）→ `inject`（看 get 是否变）。
3. 记录：**哪一层开始出问题**。练 3 轮，这套框架就长在脑子里了。
