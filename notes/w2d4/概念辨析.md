# W2D4 概念辨析：Stub 与 Binder、强弱类型

> 黄金链路精读时冒出来的两个概念问题。单独成篇，方便回看。

---

## 一、Stub 是什么，和 Binder 的关系

**一句话：Binder 是传输管道，Stub 是「收件端」骨架，Proxy 是「发件端」封装。**

AIDL 从一个 `.aidl` 文件生成三样东西：

```java
// 你写的 .aidl
interface ICarProperty {
    CarPropertyValue getProperty(int prop, int zone) = 3;
}
```

```java
// 生成的三个东西
public interface ICarProperty { ... }                       // ① 纯接口

public abstract class Stub extends Binder implements ICarProperty {   // ② 服务端骨架
    public IBinder asBinder() { return this; }
    public static ICarProperty asInterface(IBinder obj) { ... }
    @Override public boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
        switch (code) {
            case 3: {                          // getProperty 的事务码
                int prop = data.readInt();
                int zone = data.readInt();
                CarPropertyValue v = this.getProperty(prop, zone);  // ← 调你实现的抽象方法
                reply.writeTypedObject(v, 0);
            }
        }
    }
    public abstract CarPropertyValue getProperty(int prop, int zone);  // 你来实现
}

public class Proxy implements ICarProperty {   // ③ 客户端封装
    private IBinder mRemote;
    public CarPropertyValue getProperty(int prop, int zone) {
        Parcel data = ...; data.writeInt(prop); data.writeInt(zone);
        mRemote.transact(3, data, reply, 0);   // ★ 真正跨进程
        return reply.readTypedObject(...);
    }
}
```

| 概念 | 是什么 | 本链路里 |
|---|---|---|
| **Binder** | kernel 的 IPC 机制，`IBinder` 是句柄 | 跨进程"管道"本身 |
| **Stub** | `extends Binder`，`onTransact` 收包并分发到你的方法 | `CarPropertyService extends ICarProperty.Stub` |
| **Proxy** | 持远端 Binder，方法调用打包 `transact` 过去 | `CarPropertyManager` 里的 `mService` |

### 关键认知：Stub 不是"服务端专属"

**谁想「收」binder 调用，谁就 `extends ...Stub`**：

- `CarPropertyService extends ICarProperty.Stub` → CarService 收 App 调用（正向）
- `CarPropertyEventListenerToService extends ICarPropertyEventListener.Stub` → **App 收 CarService 调用**（反向）

`registerCallback` 把 `CarPropertyEventListenerToService`（一个 Stub = 一个 Binder）传给 CarService，CarService 拿它 `transact`，就落回 App 进程的 `onEvent`。**这就是"推送"在 binder 世界的物理实现。**

## 二、为什么传 `Class<E>`

**一句话：`Class<E>` 是"类型令牌"，在运行时把被擦除的泛型类型和弱类型载体重新对上，并做边界校验。和 JNI 无关。**

- 这条链路上**没有 JNI**：`App ──binder── CarService ──binder── VHAL(native 进程)`，全程跨进程。
- 真正的原因三层：
  1. **泛型擦除**：`CarPropertyValue<E>` 的 `<E>` 编译后消失，运行时拿不到。
  2. **弱类型载体**：VHAL 的 C++ union 镜像成 AIDL 的 `RawPropValues`（int32[]/float[]/...）。
  3. **边界校验 + 还原**：按 `Class` 从弱类型数组取字段 + `getClass() != clazz` 抛错。

```java
// VehicleHal.get（W2D3）—— 按 Class 从弱数组取字段
if (clazz == Float.class)   return propValue.getFloatValue(0);
else if (clazz == Integer.class) return propValue.getInt32Value(0);

// CarPropertyManager.getProperty（W2D4）—— 边界校验
if (propVal.getValue().getClass() != clazz) throw new IllegalArgumentException(...);
```

**因果链**：`C++ union（弱）→ AIDL 数组（弱）→ Java 泛型擦除（还弱）→ Class 令牌（捞回强类型）`。

## 三、怎么理解强弱类型

**本质区别：类型信息什么时候确定、谁负责查错。**

| | 强类型 | 弱类型 |
|---|---|---|
| 类型何时定 | 编译期 | 运行期（靠 tag） |
| 谁查错 | 编译器 | 你（用 tag 判断） |
| C++ 锚点 | `float speed;` | `union` / `void*` |
| 本链路锚点 | `CarPropertyValue<Float>` | AIDL `RawPropValues` 数组 |
| 出错表现 | 编译不过 | 运行期读错字段/崩溃 |

### C++ 锚点

```cpp
// 强类型：编译器知道，写错编译报错
float speed = 22.5f;
speed = "fast";   // ❌ 编译期报错

// 弱类型：union/void*，编译器不知道，你自己记得
union Value { int i; float f; char* s; };
Value v; v.f = 22.5f;
float x = v.i;    // ❌ 编译不报错，运行期读成垃圾
```

### 为什么车控属性天生弱类型

VHAL 要服务几百种属性（车速 float、档位 int、VIN string、车门 bool…），不可能一种属性一个 C++ 类型，所以用**「带 tag 的 union」**统一表示：

```cpp
struct VehiclePropValue {
    int type;              // tag：FLOAT / INT32 / STRING / ...
    union { int32_t i; float f; char* s; } value;
};
```

这个弱类型一路流到 Java：C++ union → AIDL `RawPropValues` → Java `CarPropertyValue`（内部还是弱 + `propertyType`）→ **App 传 `Class<E>` 才变强**。

### 从弱到强的三步

```java
// ① 配置声明类型：PERF_VEHICLE_SPEED → FLOAT；GEAR_SELECTION → INT32
// ② 传 Class 令牌
CarPropertyValue<Float> v = mCarPropertyManager.getProperty(Float.class, SPEED, GLOBAL);
// ③ API 取字段 + 校验
```

---

**一个记忆点**：强弱类型不是"好不好"，是**「类型信息放编译期还是运行期」的选择**。车控属性选弱类型，是因为"一种属性一个类型"不现实；代价是类型信息靠 `type` tag 一路带着，到 App 边界再靠 `Class<E>` 令牌捞回强类型。
